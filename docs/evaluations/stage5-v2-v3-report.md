# Stage 5：Skill v2/v3 留出配对评测

评测日期：2026-09-10

正式批次：`stage5-v2-v3-isolated-r4`

模型：`qwen3.5:9b`

## 结论

在 16 个冻结场景、2 个 Skill 版本和 2 次重复组成的 64 条真实 Docker Compose 试验中，64 条均完成且有效。v2 与 v3 的恢复成功率、根因准确率和安全拦截率相同；v3 没有带来可测质量提升，但每次成功的 Token 成本高 9.6%，平均成功延迟高 7.1%。因此本批次不能支持“v3 优于 v2”的结论。

组合 Redis+MySQL 故障是明确的能力边界：两版都先识别并恢复 Redis，但现有确定性工作流一次只生成和执行一个修复目标，MySQL 仍不可用，独立探针因此判定恢复失败。

## 方法与防污染措施

- 冻结 16 个服务端案例：6 个 held-out/反证、2 个 regression、8 个安全门。
- 每个案例对 v2/v3 使用同一随机 seed；重复轮次反转 arm 顺序，抵消固定先后偏差。
- expected label 只保留在 runner 内部，不进入 plan、trial spec、模型输入或 Skill 内容。
- 每条真实故障先等待 Prometheus 确认故障指标，再开始计时和模型调查。
- CPU 场景排在依赖故障之前，并要求 Loki 最近两分钟不存在 Redis/MySQL 错误日志。
- 每条试验结束后恢复三项业务服务、Redis、MySQL 和健康指标基线。
- 失败与超时保留在质量和成本分母；基础设施异常保留在原始记录并单独统计。
- 恢复成功必须同时满足工作流 `verified=true`、服务健康、目标运行和独立依赖探针通过。
- 每条结果实时追加并 `fsync` 到 checkpoint；完成后生成只读 JSON/JSONL/Markdown 产物，输出目录不可覆盖。

## 实验中发现并修复的问题

早期批次发现 MySQL 被 actuator 以 `SIGSTOP` 暂停时，TCP 连接可以建立但握手不再响应。原健康检查只配置连接建立超时，整个 `aiomysql.connect()` 可能悬挂到外层 HTTP 超时，导致 `dependency_up` 保留旧值 `1`。本轮为完整握手增加 1 秒硬超时，并加入回归测试。真实验收中，order-service 随后在约 1 秒内返回 `mysql=false`，Prometheus 第 3 次一秒轮询观测到 `dependency_up=0`。

## 可用于简历的口径

> 设计并落地多 Agent AIOps 的留出配对评测体系，冻结 16 类故障/反证/安全场景，对 Skill v2/v3 完成 64 条真实 Docker Compose 试验；两版各 32 条且无无效样本，单故障恢复 10/10、RCA 16/16、安全门 16/16，识别组合故障 0/2 的单目标闭环瓶颈，并发现、修复 MySQL 暂停时握手超时导致的监控假健康问题。

如需强调工程决策，可补充：

> 通过共享 seed、交替执行顺序、故障指标准入、独立恢复探针、Wilson 置信区间和 Token/延迟成本核算，验证候选 v3 在等质量下 Token/成功增加 9.6%、平均成功延迟增加 7.1%，据此给出“不优于基线”的评测结论，避免只凭少量成功案例宣称效果提升。

## 不能声称的内容

- 不能声称 v3 提高了恢复率或 RCA 准确率；两版质量指标相同。
- 不能把 83.3% 描述为生产 SLA；每版恢复样本只有 12 条，95% CI 较宽。
- 不能声称支持组合故障自动闭环；组合 Redis+MySQL 每版均为 0/2。
- 不能把本机 Qwen3.5 9B 与本地 Compose 的延迟外推到生产集群或其他模型。
